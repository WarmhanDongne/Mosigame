## 범위와 현재 판단

사용자는 서버만 수정해 출시 앱을 유지하던 범위에서, 업데이트할 앱과 Functions를
함께 개선하는 진단·계획을 요청했다. 새 Firebase 프로젝트에서 검증하고 운영은 유지한다.
이번 기록은 소스 조사와 설계 제안이다. 새 제품 코드 수정·테스트·운영 조회·배포는 하지 않았다.
과거 FULL 통과는 과거 후보의 근거이며 아래 계획 구현의 완료 근거가 아니다.

가장 직접적으로 확인한 결함은 게임 화면 재시도가 transport 복구를 실행하지 않는 점이다.
다른 앱으로 나가면 연결을 false로 표시하고 transportRecovering=true를 설정한다.
복귀 시 최초 복구가 실패하면 해당 상태가 남고, 게임 재시도는 구독/에셋 준비만 재실행한다.
준비 평가는 transportRecovering 중 중단되므로 버튼을 눌러도 회복되지 않는 경로가 있다.
다만 실제 사용자의 모든 장애가 이 한 경로에서 시작됐다는 운영 근거는 없다.

## 목표 동작

- 잠깐 앱을 나가도 membership·좌석·손패를 유지한다. 복귀자는 최신 서버 턴으로 복구하고 다른 휴대폰의 진행을 막지 않는다.
- 명시적 퇴장/추방과 잠깐 단절을 분리한다. 실제 종료·추방된 참가자는 자동으로 재가입시키지 않는다.
- 자동 복구와 수동 재시도는 같은 복구 절차를 이용하며 중복 실행은 한 작업으로 합친다.
- 분배 중 휴대폰은 요구한 배경 화면만 보인다. 분배 완료 후 현재 게임의 손패와 화면 준비가 확인되면 플레이 UI를 연다.
- 새 게임/다시하기/종료가 확정되면 이전 게임의 Future, 구독 이벤트, 연출 완료 콜백, 대기 명령이 새 게임을 변경하지 못한다.
- 종료·나가기는 플레이 준비 완료를 기다리는 순환 의존 없이 실행 가능해야 한다. 서버 권한·방/게임 세대 검증은 유지한다.

## 실행 순서

### 0. 환경 분리와 기준 고정

새 프로젝트 ID가 주어지면 앱 빌드 설정과 Functions 배포 대상을 함께 분리한다.
현재 FirebaseBackend는 server/local만 지원하고 server는 기본 Firebase 앱을 사용한다.
`.firebaserc` 별칭만 바꿔서는 앱 설정이 바뀌지 않는다. Android/iOS Firebase 설정,
Auth, RTDB URL, Firestore/Storage, Functions 리전, 보안 Rules/인덱스를 함께 확인한다.
새 프로젝트용 테스트 데이터만 사용하고 실제 사용자 데이터/계정을 복제하지 않는다.
테스트 앱 표시·앱 식별자·저장된 방/접속 식별자의 환경 구분도 설계한다.
배포 명령은 project ID를 명시하고 테스트 작업에서 운영 ID 선택 시 중단하도록 한다.
운영 함수별 실제 배포 후보와 로컬 미배포 후보 목록을 구분해 기준을 고정한다.

### 1. 공용 연결 복구를 먼저 수정

RoomProvider의 복구 실행 소유권은 유지하고 공용 GameSessionController의 retry에서
실제 reconnect 완료 → 현재 identity 적용 → 필요한 구독 복원 → 현재 public/private
일치 → 화면 준비 → ready 승인 순으로 연결한다. 모든 콜백을 무작정 병렬 실행하지 않는다.
이미 정상인 연결/구독/에셋은 재생성하지 않고 실패한 단계부터 재개한다.
동시 lifecycle/네트워크 이벤트/버튼 재시도는 단일 복구 작업에 합친다.
복구 시도 ID와 방·참가·접속·게임 세대로 늦은 응답을 무효화한다.
단계별 오류를 보존하고 재시도 가능한 실패와 확정된 종료/추방을 구분한다.
종료/퇴장 의도가 있으면 자동 join보다 결과 확인을 우선한다.

### 2. 게임 시작·분배·다시하기 경계를 통일

로컬 진행 명령과 연출의 식별자를 gameInstanceId/phaseSeq 중심으로 정리한다.
서버 명령 ID는 같은 논리 요청의 재전송에서 유지하며 새 게임에는 새 명령을 쓴다.
태블릿 연출 완료와 서버 완료 알림 성공을 별도로 기록한다. 연결/준비 대기 자체가
전송 실패 횟수를 소모하지 않게 하고 준비가 회복되면 미확정 알림을 다시 보낸다.
응답 유실 때는 기존 명령 결과 또는 현재 snapshot을 확인하며 새 손패를 다시 만들지 않는다.
public/private 도착 순서가 달라도 같은 게임 문맥끼리만 결합한다.
LP·FC의 반복 시작과 상호 교체를 동일한 회귀 시나리오로 검증한다.
서버 start의 전체 교체·중복 방지 계약은 보존하고 관측된 결함만 보완한다.

### 3. 종료·초기화를 복구 가능한 별도 작업으로 처리

연결이 유효하면 화면 준비 실패 중에도 종료/퇴장을 전송한다. 연결이 무효하면 필요한
접속 복원과 종료를 직렬 실행하되 게임 연출/ready 승인을 종료의 선행조건으로 두지 않는다.
요청 전 저장한 대상 방/게임과 작업 ID를 유지하고, 응답 유실 때 결과를 조회한다.
다른 게임이 이미 시작됐으면 오래된 종료를 새 게임에 적용하지 않는다.
게임 종료·방 종료·이 기기의 로컬 연결 정리는 버튼 문구와 실제 동작을 구분한다.
종료 확정 시 로컬 대기 타이머/연출/알림을 정리하고 실패 시 재시도 가능한 상태로 돌아온다.

### 4. 서버 복구 정책 정리

준비 실패로 정상 연결을 끊어 클라이언트 재연결을 유도하는 우회 처리는 신규 설계에서
기본 수단으로 쓰지 않는다. 미배포 startup watchdog도 활성화 전에 제거/대체 여부를 결정한다.
membership, transport presence, 게임 화면 준비, 게임 진행을 별도 책임으로 유지한다.
휴대폰 이탈은 개인 복구로 처리하고 서버 턴 제한/기존 timeout 규칙으로 진행을 보장한다.
controller 이탈 정책은 별도다. 진행 UI와 연출을 소유하므로 휴대폰 정책을 그대로 복제하지 않는다.
서버 timeout/중단 해제도 중복·옛 이벤트·종료 게임에 안전한지 확인한다.
기존 정상적인 세대 검증/멱등성/트랜잭션은 유지한다.

### 5. 대기 시간과 화면 피드백 개선

복구 단계별 p50/p95와 호출 수를 측정해 서버 실행, 네트워크 왕복, 데이터 수신,
에셋 준비, 연출 대기를 분리한다. 목표 수치는 테스트 프로젝트 기준값 측정 후 정한다.
준비된 에셋 재사용, 불필요한 전체 재구독/ready 중복 전송 억제, 독립 읽기 병행을 검토한다.
정합성을 위해 필요한 신원/명령 결과 조회는 근거 없이 제거하지 않는다.
카드 분배 중 휴대폰 배경만 표시하는 연출 요구를 유지하되, 실제 실패나 복구 대기가
길어지면 해당 휴대폰에 간결한 진행/재시도 안내를 표시한다. 다른 기기 입력은 막지 않는다.
다시 시도는 한 번만 실행하고 진행 중 상태·결과를 표시한다. 서버 승인 전 카드 결과를
성공처럼 보여 주는 연출은 피한다. 연결 복구 후 완료된 분배 연출은 반복하지 않는다.

프로젝트 배포·기기 검증 순서다. 최소 반복 회수와 성능 기준은 실측 계획에서 고정한다.
진단에는 단계/결과/소요 시간과 테스트용 상관 식별자만 남기고 카드·토큰·개인정보는 제외한다.

## 운영 전환 조건

테스트 프로젝트 분리는 개발 중 운영 영향 방지 수단이다. 출시 앱이 나중에 기존 운영
프로젝트를 사용할 때는 구버전 앱과 신버전 앱이 공존한다. 공용 함수 계약을 무조건
덮어쓰지 않고 기존 요청 형식 유지 또는 버전별 경로/기능 활성화 방식을 검증한다.
앱/함수/Rules 배포 순서와 각각의 되돌림 기준을 준비한 뒤 별도 운영 배포 승인을 받는다.
근거 없는 전체 DB 초기화나 추가 강제 연결 종료로 장애를 숨기는 방식은 채택하지 않는다.
